# Kolejka rozbudowy silnika

Kolejność ustalona po wymaganiach o avatarze i narzędziach runtime. Niezależne zakresy mogą być implementowane równolegle przez agentów; współdzielone integracje, buildy i przeglądy są koordynowane. Checkbox oznacza ukończony i sprawdzony etap, nie sam dokument projektu.

1. [x] **Audyt OneJS i inspektor sceny runtime.** [Audyt](onejs-coverage-audit.md). Pierwszy batch: otwarcie F1, aktualna scena, GameObjecty, realna hierarchia Transform3D, komponenty i podgląd transformacji. Bez edycji/fizycznych teleportów.
2. [x] **Edycja transformacji i historia zmian.** Typowane pola Transform2D/Transform3D, walidacja, undo/redo do 256 wpisów i izolacja scen/komponentów. Właściciele ruchu blokują bezpośrednie zmiany; teleport i edytory innych komponentów wymagają jawnych adapterów. Sprawdzone pełnym buildem (411 testów) oraz native inspectorSmoke, nie dowolna refleksyjna instancjacja klas.
3. [x] **Gizmos 2D/3D.** Przesuwanie, obrót/skala, local/world, snapping i ekranowy wybór rzutowanych osi. Klawiatura F1 → Stage → pointer gizmos → gra. Gest to jedna operacja undo; zmiana rodzica/sceny/kamery/viewportu lub focus loss anuluje go. Nieprzedstawialne konwersje i obiekty sterowane ruchem są jawnie odrzucane. Szczegóły ograniczeń i dowodów: runtime-tools.md.
4. [x] **Eksport runtime SceneJson.** Istniejące SceneJson i jawne codeki, zagregowany preflight bez pomijania danych oraz jawny cel z atomową podmianą. Plik jest snapshotem runtime; assety wymagają codec/resolvera dostarczonego przez hosta. Szczegóły i ograniczenia: [runtime-tools.md](runtime-tools.md).
5. [x] **Avatar i FPS/TPP — szczególny priorytet użytkownika.** [Projekt](superpowers/specs/2026-10-15-avatar-layers-design.md): animacja kontra widoczność, poddrzewa kości, części/ubrania/sockety, ARMS_ONLY/FULL_BODY, jedna skinned mesh, F5, viewmodel i kamera. Nie usuwa to wcześniejszych wymagań avataru; implementacja zachowuje kolejność tej listy. Etap A jest wdrożony i sprawdzony: złożone maski animacji, części/sloty/sockety oraz niezależne widoki nad kanoniczną instancją. Etap B także jest sprawdzony: podział jednej skinned mesh na autorskie regiony, zachowanie kanonicznego skinningu, testy pikseli oraz zasobów na GL20 i GL30. Etap C jest zatwierdzony: autorska ważona postać, F5 FPS/TPP, osobny pass rąk/narzędzia, jedna kanoniczna poza, sloty/sockety i kamera z konserwatywnym sweepem. Sprawdzone 454 testami, GL20/GL30, voxelSmoke i inspectorSmoke; regresje obejmują powtarzany skok i cleanup anulowanej przebudowy chunków. To proceduralne demo, nie walidacja importowanego rigu produkcyjnego.
6. [x] **Fizyka 3D.** [Projekt Bullet](superpowers/specs/2026-10-15-physics3d-player-design.md): scene-local fixed step, body/collidery, zapytania, kontakty i cleanup; następnie osobny adapter chunków. Etap A jest zatwierdzony: opcjonalny moduł brył i colliderów, stały krok, jawne polecenia oraz cleanup; 20 rzeczywistych testów natywnych Bullet i pełny reactor (474 testy). Etap B także jest zatwierdzony: kontakty enter/stay/exit, osobne triggery, maski/materiały oraz kopiowane wyniki raycastów i sweepów; 38 testów natywnych Bullet i cały reactor (492 testy). Etap C1 także jest zatwierdzony: niezależne rewizje/snapshoty chunków, opcjonalny bridge kolizji i jawna polityka gotowości; pełny reactor 504 testy oraz voxelSmoke. Gotowość nie stanowi fizycznej bariery dla zwykłych ciał dynamicznych. Etap C2 jest zatwierdzony: osobny natywny kontroler kapsułowy, skok/schody/pochyłości, kamera/query/trigger integration i egzekwowana gotowość omiatanej objętości; pełny reactor 529 testów, w tym 65 testów modułu fizyki i 8 bridge. C3 ma opt-in demo/debug draw oraz realny Bullet/OpenGL smoke: widoczny spadający sphere i kinematic platform, compound body, action trigger, edycję voxel i avatar FPS/TPP. Smoke odtworzył scenę i potwierdził ruch pikseli, overlay, F5 clearance, socket pose oraz usunięcie śledzonych zasobów GL. C3 i cały desktopowy etap fizyki są zatwierdzone po niezależnym przeglądzie, pełnym buildzie (530 testów) i ponownym physics3dSmoke. Dowody obejmują rzeczywisty czerwony trigger oraz niepustą maskę pikseli bryły w obu pozycjach i kontrolę z wyłączonym rendererem. Android jest poza zakresem. Obecny voxel FPS/AABB nadal jest niezależnym trybem.
7. [x] **Feel i animacje — zakres desktopowy zakończony.** Kanały prezentacji modeli/kamer, presety Feel 3D, particles/postprocessing, PCM/FFT, kontrakt haptics i Shapes mają implementację oraz właściwe testy/przeglądy opisane niżej. Presety Feel 3D uzyskały niezależną akceptację FIX1. Nie deklarować pełnego katalogu Feel/Animancera. Produkcyjny rig/import i testy widoczności pozostają osobnymi dowodami względem modelu proceduralnego.
8. **Android.** [Wyniki i blokady](android-status.md): ograniczona aplikacja, Yoga JNI i host JS/QuickJS mają buildy oraz testy JNI/ART; smoke modelu/dotyku przeszedł przy density 160 i 320, a rzeczywista utrata/odzyskanie EGL sprawdziła VAO/shadery/model/UI/SDF/font/depth FBO. ActivityFIX3 i responsiveFIX1 są zintegrowane i zatwierdzone; dwa odtworzenia Activity na finalnym APK density 320 przeszły osobno ([na pierwszym planie](artifacts/android/app-activity-foreground-instrumentation.txt), [po pauzie](artifacts/android/app-activity-paused-instrumentation.txt)). Osobny test układu poziomego przy density 320 także przeszedł (53.573 s; [log](artifacts/android/app-landscape-instrumentation.txt)), sprawdzając tę samą Activity/fixture, kompaktowy odstęp, obszary SDF, fizyczny target co najmniej 60 oraz przywrócenie portretu przy 54 logical. Rzeczywista utrata/odzyskanie EGL na wątku właściciela także przeszła osobno przy density 320 (54.787 s; [log](artifacts/android/app-final-egl-instrumentation.txt)); osobny test touch/model/React, multipointer i pełnej generacji zasobów przeszedł w 63.666 s ([log](artifacts/android/app-final-touch-instrumentation.txt)). Wszystkie pięć przypadków aplikacji density 320 przeszło osobno. Łączny runner nie jest zaliczony: próba całego zestawu zakończyła się ANR przy starcie, a próba klasy dwóch testów — ANR przy focus. Debug/test + R8 release build oraz audyty pakowania debug/release PASS. Ograniczony runtime R8 release przeszedł na lokalnie podpisanej kopii APK: [szczegóły i dowody](artifacts/android/app-release-runtime-verification.json); nie była to publikacja release. Fizyczny ARM, pomiary wydajności, pełne GLES Shapes oraz adaptery MapLibre i Bullet na Androidzie pozostają poza zakresem potwierdzenia.

## UI a obiekty sceny — korekta zakresu użytkownika

Osobne drzewo UiDocument/React i karta logów inspektora nie są potrzebne. Inspektor sceny nadal dotyczy GameObjectów i komponentów. UI może być kontrolowane przez komponent obiektu gry wiążący widok/panel z deklaratywnym UI; nie wymaga to GameObjecta dla każdego wewnętrznego elementu ani drugiego modelu sceny. To ustalenie zakresu, nie deklaracja wdrożonego adaptera.

Dalsze kontrolki, clipping i utilities pozostają zwykłym rozwojem deklaratywnego UI z jawnym API i testami; bez obietnicy pełnego DOM/CSS/Tailwind.

Bieżący status techniczny, polecenia i ograniczenia narzędzia: [runtime-tools.md](runtime-tools.md). Pozostały backlog migracji i szczegóły modułów: [TODO.md](TODO.md).
