# JavityEngine core unification audit

Read-only audit of base `48814ae`, clean tree, dated 2026-10-16. No build or tests run. Scope: `AGENTS.md`, Gradle settings/builds, `docs/migration-api.md`, `docs/engine-guide.md`, and source/dependency/import references.

## Finding

There is already one modern gameplay core: `javity-core` (`org.javity.core.Game`, `GameObject`, `Component`). The gameplay classes do not depend on Artemis, Galaxy Rapid or the legacy engine. The javity-core module also contains portable libGDX rendering; it is not a graphics-free artifact. Its component contract already covers multiple same-type components, subtype queries, stable scene indexes, tags, deterministic lifecycle, UI/WORLD update modes and explicit lookup/removal. `docs/java-lab-component-parity.md` is the most precise existing contract audit. The architectural issue is that the default Gradle reactor and desktop runtime still include the historical core stack, and the repository contains two APIs named Component/GameObject with separate lifecycles.

The desired shape should keep `javity-core` as the only gameplay object/component model, with optional capability modules layered on it: `javity-physics2d`, `javity-physics3d`, `javity-voxel`, `javity-map-core`, `javity-assets`, UI and scripting providers. This is consistent with existing dependency direction (`physics2d -> core`, `physics3d -> core`, `voxel -> core`, `map-core -> core`, `assets -> core`) and does not imply one large jar. MapLibre is a separately optional native renderer, not a gameplay core.

## Current graph and concrete remaining legacy

- `settings.gradle` includes `javity-backend`, `javity-engine`, `javity-map`, `javity-net`, and `javity-desktop` in the ordinary reactor. Android legacy, XML UI, and generator are directories outside the main settings/reactor; `AGENTS.md` says the historical Android/XML/generator remain outside it.
- `javity-engine/build.gradle` exports `javity-backend` as `api`. `javity-backend/build.gradle` exports libGDX, Artemis ODB 2.3.0, Spine 3.5.51.1, Guava and other historic libraries. `build.gradle` has the root Artemis version solely for this backend dependency. Thus any consumer of `javity-engine` gets Galaxy Rapid/Artemis transitively.
- `javity-desktop/build.gradle` directly depends on `javity-engine` only to compile the old demo (`DemoApplication`, `DemoScene`), while all modern demo types separately depend on `javity-core` and optional services. `DesktopLauncher` retains `--legacy`; `README.md` documents `--legacy --smoke`; `docs/modernization-status.md` records real GL legacy smoke evidence. `DemoScene` exercises legacy JGameObject/JComponent/SpriteRenderer plus the legacy Yoga setup. This is still a supported compatibility demo, although it is intentionally not representative of modern gameplay.
- `javity-map/build.gradle` exports `javity-engine` and implements a legacy OSM/plugin model in `pl.radomiej.map` (12 main Java files). `MapComponent`, `LayerComponent`, `TileComponent`, `Marker`, `JMap`, `MapScene`, `AddMarkerComponent`, etc. use old JComponent/JGameObject/JSceneManager/JResources/JCamera/JInput/JTime, and `MapComponent` also imports Galaxy Rapid Box2D/Shape components. It depends on `javity-net`. The modern `--map` demo is `javity-desktop/.../MapDemo.java` and uses `javity-map-core`; it is not this old plugin. The old module remains in the reactor as a compatibility API, but desktop does not depend on it.
- `javity-engine` has 77 main Java files under the public `org.javity.engine` and `org.javity.components` packages: old `JGameObject`/`JComponent`/`NativeComponent`, lifecycle/scenes/serializer/resource APIs, renderer/physics/input/audio components, remote/mobile APIs and reflection proxies. `JavityScreen` extends `RapidArtemisScreen`; `JavityApplication` extends RapidApp; rendering/resources/physics bridge to Galaxy Rapid. The engine also uses Kryo and transitively exports backend. This is an API surface, not dead code that can be deleted without a compatibility break.
- `javity-backend` has 96 main Java files under `galaxy.rapid`, including app/screen navigation, event bus, RapidAsset, cameras, Sprite/Text/Spine renderers, Box2D, Artemis systems and tests. `javity-engine` is its in-reactor consumer. It is a local Galaxy Rapid fork/backend, not libGDX itself.
- Out-of-reactor users remain: `javity-xml-ui` imports old engine and Galaxy Rapid; `javity-android` uses old mobile intent/geolocation/input APIs; project-generator templates import old JavityApplication/JScene. These directories are not included by current settings, but their source is evidence that deleting the legacy API breaks currently retained migration material. Check their own build/package workflows before removal.
- `javity-net` is old standalone support consumed by `javity-map`; the new map-core HTTP fetcher is independent. `javity-map` and `javity-net` are not dependencies of desktop's modern map demo.
- Runtime modern import/dependency graph has no `org.javity.engine`, `galaxy.rapid` or Artemis requirement, except the explicitly legacy desktop demo. Existing `javity-core` is already the intended singular gameplay core; don't merge optional render/physics/map/native providers into it.

Useful source pointers: `settings.gradle`; root `build.gradle`; `javity-engine/build.gradle`; `javity-backend/build.gradle`; `javity-desktop/build.gradle`; `javity-map/build.gradle`; `javity-desktop/src/main/java/org/javity/demo/DesktopLauncher.java`; `DemoApplication.java`, `DemoScene.java`; `docs/java-lab-component-parity.md`; `docs/modernization-status.md`; `README.md`; `javity-map-core/src/main/java/org/javity/map`; `javity-android-app/README.md`.

## Supported functionality and migration gaps

`docs/migration-api.md` is explicit that the new core equivalents exist for most gameplay basics, but arbitrary old games and historical serialized scenes are not converted. Current gaps or compatibility-only areas that block deleting all old sources include:

- Whole-game scripts and lifecycle/API names: JGameObject/JComponent/NativeComponent, old `start`/`update`, global JTime/JSceneManager, proxy/reflection semantics, and custom scene builders. Migration is source-level and needs game-specific work.
- Historical JSON/Kryo scene loading and class-name/reflection conventions. New `SceneJson v1` requires explicit codecs; do not promise old save import by deleting serializers.
- Spine legacy renderer and assets: old runtime is 3.5.51.1 while exported examples identify Spine 2.1.27. Modern API replacement does not establish asset compatibility; re-export/license review is needed.
- Old geographic OSM plugin: modern raster map-core covers view/tiles/cache/markers/routes and HTTP provider, and MapLibre covers a separate vector use case; GeoJSON/plugin integration and old game call sites still need deliberate mapping.
- Android intent/navigation/geolocation, XML UI, and generated project templates are not migrated into the new app/API. They sit outside the main reactor, so the desktop core migration must not silently claim them.
- Old APIs can be public consumer dependencies even where the current modern examples do not use them. A full source deletion is a major/breaking product decision, while dropping legacy from the default runtime is a smaller architecture cleanup.

Safe-to-remove from the *modern default graph* after moving the old demo source: `javity-desktop -> javity-engine`, then legacy-only runtime dependency closure on the modern desktop classpath. `javity-map` can be made opt-in / removed from the default reactor because no current modern desktop source depends on it, but deletion of its API still breaks old map clients. `javity-net` can follow the same opt-in status once no included legacy module requires it. Safe *source deletions today*: only genuinely unreferenced dead classes after a full symbol/API use review; this audit found no basis to declare all of either legacy module dead. Do not delete whole `javity-engine`, `javity-backend`, or legacy map code as an incidental side effect.

## Ordered migration (recommended)

1. **Make the new-core boundary operational.** Keep `javity-core` as the singular gameplay API; continue service modules as opt-in project dependencies. Add an explicit legacy Gradle property/source-set or separate compatibility/legacy-demo module so the ordinary reactor and modern desktop runtime do not acquire `javity-engine -> javity-backend -> Artemis`. Move `DemoApplication` and `DemoScene` with their `--legacy` launcher/smoke to that target, or retain the legacy launcher as a separately assembled application. Update settings, desktop dependencies, README and migration docs together. Keep legacy publication/source available for existing games during migration.
2. **Make compatibility modules opt-in.** Once the legacy demo is isolated, put `javity-engine`, `javity-backend`, `javity-map`, and `javity-net` behind an explicit legacy build flag or separate included build. Preserve old plugin build and source until its consumers are accounted for. Avoid making `javity-core` depend on these modules or copying Galaxy APIs into core.
3. **Migrate supported examples and consumers by capability.** Modernize real game call sites against `Game/GameObject/Component`; map old sprite/text/audio/input/physics/camera operations to their already available services. For remaining legacy map behavior, either implement specific missing behavior in optional `javity-map-core` or keep the old map adapter package. Migrate JSON/Kryo with explicit import/codecs, assess Spine asset export/licensing, then handle mobile/XML/generator separately. Remove each legacy slice only when its consumer and compatibility contract have a destination.
4. **Remove legacy sources only at an explicit breaking boundary.** When API usage, shipped game/save migration and platform consumers have been inventoried, remove the compatibility modules and their dependency versions/license notices. Before that, preserve them as a visibly legacy optional compatibility layer rather than allowing them to masquerade as the current gameplay core.

This yields a simpler normal build and one modern programming model without forcing every optional service into one artifact or making an unverified claim of full old-game migration.

## Alternatives / tradeoffs

1. **Recommended: optional compatibility layer, modern default graph.** Isolate old engine/backend/demo behind a flag or separately built app; default build and new examples depend on `javity-core` and services only. Low-risk first step, preserves existing APIs and legacy smoke. Costs retaining old code/build/test matrix temporarily.
2. **Hard cut now.** Remove `javity-engine`, backend and old plugin, legacy launcher, and out-of-reactor integrations. Fastest simplification but breaks public Java API, old games/saves and source templates, drops only proof/demo for those paths, and does not migrate their functionality. Not safe given current docs and user requirement to avoid deleting supported functionality.
3. **Absorb legacy backend into core.** Move Galaxy Rapid/Artemis/rendering into `javity-core` to get a single apparent module. Rejected: couples gameplay to rendering/backend/ECS, makes default artifact heavier and less portable, conflicts with the established dependency graph and explicit “new core without Artemis” architecture. It would collapse jars, not unify the actual object model.

## Public API impact and verification gates

The safe first change can preserve public old APIs and break only consumers that assumed `javity-engine` is an unconditional desktop dependency: they must add the legacy artifact/flag. If APIs are ultimately deleted, the break includes all `org.javity.engine.*`/`org.javity.components.*` public classes and `galaxy.rapid.*`, old serializers, old map types and generator references. New API users should target `org.javity.core` and explicit services; component-level differences in transforms, hooks, units, physics and UI are captured in `docs/java-lab-component-parity.md`.

Gates for the staged split (not run for this audit):

- Default reactor/dependency inspection proves no Artemis, Galaxy Rapid, old engine/map/net in modern desktop runtime; build/test all included modules.
- Modern native smoke gates remain distinct: modern core/render/UI; runtime (audio/assets/timers/scenes/input); physics2d; maps; plus the actual enabled optional feature demos. This repository requires GL-backed evidence for graphics; headless compilation is insufficient.
- Legacy flag/compatibility target still compiles, passes old engine/backend/map unit tests, and runs the existing `--legacy --smoke` with a real GL context if legacy is claimed supported.
- For each migrated game/API slice, run old-vs-new behavior fixtures and load representative historical JSON/Kryo data. Spine requires real licensed/export-compatible assets. Android/XML/generator need separate target-specific builds; current new Android app excludes legacy.
- Confirm packaged dependencies with `dependencies`/distribution audit, update docs/work-queue/TODO, and communicate intentional compatibility/version break before removing sources.

## Recommendation

Treat the request as **one gameplay core plus optional services**, which the modern side largely already implements. First isolate legacy demo/backend/plugin from the default application graph, while retaining them in a named opt-in compatibility build. Then migrate actual callers by feature and delete legacy slices only when their consumers, stored data and platform integrations have an explicit replacement. Do not create a `javity-everything` jar and do not merge Galaxy Rapid/Artemis into `javity-core`.
