# Browser Wasm ports: evidence and recommendation

**Checked:** 2026-10-17. Read-only source and upstream metadata review; no product changes or browser runtime proof.

## Recommendation

A browser build is technically plausible, but each native subsystem needs its own browser provider. Use TeaVM Wasm GC for the Java app and a small browser JavaScript host for package loading, rendering integration, and interop. Yoga can use Meta's official `yoga-layout` npm package (3.2.1), which ships prebuilt WebAssembly. Bullet has a concrete browser port in Ammo.js; the upstream repository includes `.wasm` output and browser demos, but the npm `ammo.js@0.0.10` tarball is a JavaScript-only bundle, so it does not satisfy a Wasm requirement by itself. Build/pin the upstream Wasm artifact or vendor a deliberately versioned build. Neither package is a drop-in implementation of Javity's Java/native API.

## Yoga

- Official package: [`yoga-layout@3.2.1`](https://www.npmjs.com/package/yoga-layout), published metadata identifies Meta Open Source, MIT, and `facebook/yoga` as upstream. [Upstream README](https://github.com/facebook/yoga) links this package.
- The published package README states “prebuilt WebAssembly bindings,” documents `import {Yoga, Align} from 'yoga-layout'`, requires ES modules and top-level await (or `yoga-layout/load`), and requires explicit `free()` / `freeRecursive()` ownership. The 3.2.1 tarball contains `dist/binaries/yoga-wasm-base64-esm.js` (120,919 bytes) plus ESM wrappers; it embeds the Wasm payload rather than requiring a separately fetched `.wasm` file.
- This is a good source for a browser `YogaBackend`: Javity's `YogaBackend`/`YogaNode` are already opaque, and the repo uses Yoga 3.2.1 on Android. Still, implement and map the current full Java contract, including measure callbacks, child insertion/removal, layout getters, styles, subtree freeing and error/lifetime behavior. Existing LWJGL and Android providers call JNI; neither works in a browser. `javity-ui` also uses libGDX Scene2D/FreeType, so Yoga alone does not make UI browser-ready.
- The unrelated `yoga-layout-wasm@1.9.3-alpha.7` is an older third-party package; prefer the official 3.2.1 package.

## Bullet

- Current Javity provider is [gdx-bullet 1.14.2](https://github.com/libgdx/libgdx/tree/master/extensions/gdx-bullet), using generated JNI/SWIG bindings and native platform libraries. `javity-physics3d` directly uses its `com.badlogic.gdx.physics.bullet.*` classes; there is no `Physics3DBackend` SPI. This cannot run through JNI in a browser or become portable through TeaVM.
- [Ammo.js upstream](https://github.com/kripken/ammo.js) describes a direct Bullet-to-JavaScript port via Emscripten, includes `builds/ammo.wasm.js`, `builds/ammo.wasm.wasm`, a WebAssembly browser demo, and says the binding API is autogenerated from Bullet. GitHub metadata on 2026-10-17: branch `main`, HEAD `c8779e60159d428f11ff1eb553dc9b6b6e2d317a`, last pushed 2026-09-22. Upstream README identifies zlib licensing (same as Bullet).
- Registry metadata reports `ammo.js@0.0.10`; inspecting its published tarball shows only `package/ammo.js` (1,561,971 bytes), with no `.wasm` artifact. Its upstream README also says only classes listed in `ammo.idl` are exposed. Pinning only the npm version would therefore select a JS bundle and a partial binding surface, not a browser Wasm build. The project source can build Wasm with Emscripten; alternatively pin an exact upstream commit/build and preserve the matching JS glue + `.wasm` file together.
- Ammo's generated JS API (`Ammo.btVector3`, `btDiscreteDynamicsWorld`, etc.) is a different binding model from libGDX's Java `bt*` wrappers. Reimplement Javity's physics behavior behind a new browser-specific adapter, or introduce a true portable physics SPI first. Verify the existing public behavior: fixed 1/60 stepping, body/collider shapes, contacts/triggers, mutual 16-bit filters, ray/sphere/capsule queries, kinematic/controller semantics, cleanup, and copied result ownership. API-name overlap does not establish semantic parity.
- A Java port exists at [`vbousquet/libgdx-jbullet`](https://github.com/vbousquet/libgdx-jbullet), described by its author as a Java Bullet port for libGDX/GWT. This is a possible JS/GWT research branch, not evidence of a TeaVM/Wasm-GC build, not the official current `gdx-bullet` module, and not proof against Javity's Java 25 / current libGDX dependencies. Prefer Ammo as the known browser-Wasm candidate; consider jBullet only if avoiding a JS/Wasm physics boundary justifies separately proving TeaVM compatibility and behavior.

## TeaVM, JavaScript and existing host

- Existing repo audit [`browser-wasm.md`](../../../docs/audits/2026-10-17-consolidation/browser-wasm.md) records the released compatibility pairing `gdx-teavm 1.6.1` + `libGDX 1.14.2` + `TeaVM 0.15.0`, and distinguishes `js {}` from `wasm {}` targets. It says the repo has no browser target yet and that Wasm GC still uses a JS loader/runtime and interop boundary. TeaVM Java 25 support does not establish this app's build compatibility.
- The user's public [`Radomiej/java-lab`](https://github.com/Radomiej/java-lab) is a different mechanism: its worker loads vendored TeaVM Playground compiler assets, compiles Java source in-browser, calls `generateWebAssembly`, then hosts the generated module in a Web Worker. Java exports `tick`, `frame`, `setKey`, `resize`, and `dispose`; the JS worker maps `frame()` text commands (rect/sprite/text/collider etc.) to browser messages and JS draws them on Canvas 2D. Its runner-worker boundary is a useful lifecycle/input/error pattern, but it is not libGDX, not a general TeaVM application target, and does not already bridge npm Wasm modules or GL/WebGL rendering. `java-lab` HEAD at review was `3a4c8a8ac3bec6a0cbd23bd24fc8b2464b03f379`; it vendors the compiler wasm/runtime/class library from [`konsoletyper/teavm-javac`](https://github.com/konsoletyper/teavm-javac) (HEAD `208d4c97a602ba0df055f16e6882059fb69d0122`) / TeaVM Playground. This compiler-in-the-browser arrangement should not be confused with compiling this repository's app for Wasm GC.
- Current Javity script contract [`ScriptUiEngine`](../../../javity-script/src/main/java/org/javity/script/ScriptUiEngine.java) is synchronous `evaluate`/syntax checking plus registered host functions. The Graal provider is desktop-only and QuickJS provider Android-only; neither is browser-ready. For a browser app, use the page JS runtime through an explicit TeaVM JS interop/provider seam or keep React/JS as the browser host and expose narrow Java exports. The JavaLab technique suggests isolating JS transport/lifecycle in a worker, but does not mean Java can directly evaluate page JS without a bridge.

## MapLibre and smallest proof

- The existing GL JS reference pins `maplibre-gl@6.14.0` in [`web/maplibre-reference/package.json`](../../../web/maplibre-reference/package.json). It is a separate reference renderer; repo docs explicitly say DOM/WebGL MapLibre GL JS is not embedded in the game. A browser integration means loading GL JS in the page and defining a JS/DOM/canvas bridge; it does not reuse MapLibre Native's Linux EGL/FFI path or automatically share Javity's WebGL context.
- Smallest useful future proof: create an isolated browser target and host page, compile a tiny Java scene with the pinned TeaVM Wasm-GC pairing, then load Yoga 3.2.1 and one Ammo Wasm build from JS. Through explicit adapters, create/layout/dispose a small Yoga tree and create/step/query/dispose one Bullet world; compare results to current Java tests for equivalent supported cases. Exercise Java↔JS calls and Wasm asset loading in a real browser. Keep MapLibre GL JS as a separate page layer behind a map facade and replace Graal with the browser's JS host/provider. First prove dependency isolation and compile, then prove actual browser runtime; do not infer compatibility from upstream package presence alone.
