# JavityEngine multiplayer rooms architecture audit

**Scope.** Read-only architecture review of the current repo, considering Colyseus as the intended room/matchmaking technology. No code, builds, or dependency changes were made. “LeagueSu” was clarified by the user as Colyseus. The review does not assume that the simulation authority should move from Java to JavaScript.

## Findings in the repo

- docs/multiplayer-design-notes.md explicitly says multiplayer is still a project: no transport, headless server, or replication exists. It proposes per-side Games; server-authoritative spawn/despawn; session networkId separate from GameObject.id; declared authority; typed/versioned replicated fields; validated client commands; snapshot tick IDs; late-join baseline; and interpolation. It expressly defers prediction/reconciliation and rejects Box2D lockstep assumptions.
- Game is a useful scene-local simulation owner. Game.addSystem must happen before start; step(delta) gives a bounded delta, has distinct UI/before/WORLD/after/late phases, snapshots components/system lists, and cleans up scene-owned systems in reverse registration order. These are good building blocks for a room tick, but the public API has no thread synchronization or room/network lifecycle. See javity-core/src/main/java/org/javity/core/Game.java and GameSystem.java.
- GameObject.id is a monotonically assigned int local to each Game, not a durable network ID. Components support arbitrary Java object state and public mutable transforms. There is no network codec, dirty tracking, thread-safe mutation queue, authority guard, or command validation at the core boundary. GameObject and physics should be owned by one room thread; network callbacks should enqueue validated commands for that thread.
- javity-core has a libGDX API dependency and rendering packages, but no backend dependency in its module build. Physics modules depend on core and native bindings, and do not require a renderer in the normal simulation path. Physics2D.onCreate() initializes Box2D and creates a scene-local World; it uses a fixed 1/60 step with an accumulator. Physics3D similarly owns a Bullet world with a fixed 1/60 step and a max of eight simulation steps per frame. Physics3DDebugView explicitly requires Gdx.gl20 and graphics; ordinary simulation does not. javity-desktop currently packages LWJGL and desktop natives as an application. Thus a Java headless room process looks feasible in principle, but native libraries/JDK packaging and headless startup still need an integration proof.
- javity-net is HTTP/asset download support, not a realtime room protocol. The new core has no current WebSocket transport or web runtime. Old GWT-related sources live under legacy javity-backend/project generator and do not establish that the new core, Box2D/Bullet modules, or their natives compile/run in a browser.
- Script integration is not a server bridge today. javity-script is a portable React/JS host SPI; javity-script-graal supplies GraalJS for desktop UI and javity-script-quickjs-android supplies Android QuickJS. The Graal module is a UI runtime dependency, with no Colyseus adapter, Java room host, remote call bridge, or server-side replicated-state API. Embedding a JS context in Java would still not make Colyseus’ Node room runtime and Javity’s Java simulation one process or one state automatically.
- The optional Artemis proposal keeps Artemis in an opt-in module with an explicit GameObject bridge. It does not change the room architecture: ECS entities/IDs and GameObject IDs would also need deliberate network mapping. Do not make room transport depend on Artemis.

### Recommendation

Start with Option A: Java remains the only authority for gameplay state and physics; Colyseus is the room-facing Node gateway and control plane. Make the Java↔Node boundary typed and small. For an initial slice, use one Java room process and one Colyseus room, with server-owned network IDs, one join/create path, validated input commands, a fixed room tick, and snapshot replication for a tiny DTO (for example player position/velocity plus spawn/despawn). Add late join and loss/reconnect semantics before prediction. The local developer path should exercise the exact same processes and wire boundary on loopback; a shortcut that calls Java internals directly would fail to test the deployed architecture.

A room worker should own exactly one simulation instance (Game, physics worlds, command queue, ID map and tick clock). It should process network input only at defined tick boundaries. Separate room workers/processes provide clearer isolation and failure domains than sharing mutable GameObjects across room threads. Colyseus documents multiple room instances and process selection, but a separate Java worker allocator/supervisor is project-owned work in Option A.

Treat “Create/Join/Test Locally” as a developer workflow around the room service: start local Node gateway and Java worker(s), create or join via the same API used by clients, then attach a preview client. The preview renderer must consume snapshots/events and never step or write the authoritative Game. If local single-player convenience is desired, keep it as a clearly separate local simulation mode with a local transport adapter, rather than allowing two owners of one scene.

## Portability and hosting constraints

1. **No shared physics engine across Java and JS.** Colyseus is a Node.js framework. Its documented Room state and automatic schema synchronization operate in Node. It will not invoke Java Game.step() or native Box2D/Bullet by itself. A Node process cannot share Java objects in memory without embedding/runtime bridges, which are not in this repo; a separately running Java worker necessarily needs an explicit protocol. GraalJS is a Java-side script engine and does not convert a Node Colyseus server into an in-process Java library.
2. **Browser means a client transport, not browser-hosted authority.** Colyseus’ JavaScript SDK is engine-agnostic and connects over WebSockets; server transport owns WebSocket sessions and ping/pong. A browser can host UI/preview and join a server, but cannot be trusted as the authoritative simulation. Colyseus WebTransport is documented as JS/TS-client-only today; do not rely on it for Java game clients. A standard WebSocket path is the safer cross-client baseline.
3. **Managed hosting must run both runtimes.** Colyseus’ official deploy docs describe deploying a regular Node.js application and separately explain multi-process scaling. The reviewed docs do not establish that Colyseus Cloud runs an arbitrary Java simulation sidecar/worker or supports private Node↔Java room RPC. Treat “hostable on Colyseus Cloud” for Option A as unverified until provider capabilities are confirmed. Self-hosted VM/container/Kubernetes with Node gateway and Java worker is the assumption-safe deployment. If only Colyseus Cloud is required, that constraint may force Option C or a separate external Java host, not an invisible integration.
4. **Native Java headless operation is promising, not proven.** The current core module does not include a desktop backend, but the Java runtime needs compatible libGDX native libraries for Box2D/Bullet and native access configuration. Desktop currently supplies desktop natives and --enable-native-access=ALL-UNNAMED; Android packaging is separate. Headless server build/launch, room isolation and native cleanup need actual verification before claiming deployability. Bullet/Box2D browser portability is not evidenced in this repository.
5. **Deterministic tick is not deterministic physics.** A fixed Java delta provides repeatable scheduling cadence, not bit-identical outcomes across machines, architectures, native-library versions or different contact ordering. Box2D/Bullet are not a basis for cross-client lockstep here. Server snapshots and client interpolation are sound initial goals; prediction/reconciliation must be scoped to specific gameplay controllers and tolerable correction behavior.
6. **Network identity and property authority require explicit data contracts.** A local integer object ID is insufficient. Add server-assigned session-stable ID (and ideally generation/epoch to avoid stale references), ownership and authority policy, codec/schema version, and explicit replicated fields. Spawn/despawn, ownership changes, room commands and baseline snapshots need reliable ordering; transient/high-frequency updates can use a transport’s appropriate delivery mode only after measured requirements. A client-originated transform is an intent/request until Java validates and commits it.
7. **Preview and simulation have different lifetimes.** Room creation/join/leave/reconnect/destruction should be defined independently from renderer/window lifetime. Headless worker must never initialize GL; preview close must not destroy a room unless it explicitly leaves it. On shutdown, stop accepting commands, drain/disconnect clients, then close scene systems/physics and release native resources. Fixed tick should not inherit a render frame delta or local pause/focus policy.

## Colyseus source references (official docs, current pages checked 2026-10-17)

- [Colyseus overview](https://docs.colyseus.io/) describes it as an open-source Node.js framework for authoritative game servers with state synchronization and matchmaking.
- [Create a Colyseus Server](https://docs.colyseus.io/getting-started/server) says the server runs rooms and owns their state, while clients connect; the getting-started page includes a browser Playground and create/join flow.
- [Rooms](https://docs.colyseus.io/room) documents room instances, messages, and state synchronization; it also distinguishes RelayRoom as a room without authoritative state.
- [Matchmaking](https://docs.colyseus.io/matchmaker) documents joinOrCreate, join, joinById, reservations, process stats, and standalone matchmaker.
- [Server configuration](https://docs.colyseus.io/server) documents transport, presence, storage driver and room-process selection; a standalone matchmaker delegates room creation to game-server processes via IPC, for Colyseus processes.
- [State synchronization](https://docs.colyseus.io/state) describes schema mutation tracking and full state handshake for clients.
- [Transport](https://docs.colyseus.io/server/transport) documents WebSocket transport and connection lifecycle; [WebTransport](https://docs.colyseus.io/server/transport/webtransport) says browser-side WebTransport support is currently limited to the JS/TS SDK.
- [Deployment](https://docs.colyseus.io/deployment) describes ordinary Node.js deployment and scaling considerations. It does not prove Java worker hosting support.

## Confidence / unverified items

High confidence: current repo has no multiplayer transport/replication, GameObject.id is not a network ID, Colyseus runs its rooms/state in Node, no Java/Box2D object sharing is implied by Colyseus, and local preview must not own the authoritative simulation. These follow from source and official docs.

Unverified and requiring a small integration spike: actual headless startup/shutdown of Game plus Box2D and Bullet with server JVM/native packaging; operational performance at target room count; exact Colyseus Cloud support for an external Java room-worker service; and whether an existing Java Colyseus SDK/client implementation is desired or maintained. No such integration exists in this repo, and this audit did not fetch/install candidate libraries.
