# Android port architecture and verified dependency choices

Evidence date: 2026-10-15. Read-only assessment of `/workspace/JavityEngine`; only this report and downloaded evidence under `the external verification workspace` were written. No Gradle tasks, native compilation, emulator start, engine edits, or commits were performed for this assessment.

## Decision

A real Android implementation of core + voxels + Scene2D/Yoga UI + the existing React/TSX authoring contract is feasible as code work. Keep ordinary JDK25 and GraalJS Community on desktop. Android needs an actual Yoga Android JNI backend and a different JavaScript backend. Do not put LWJGL Yoga, desktop GraalJS or the FFM MapLibre module into the APK and call that Android support.

Recommended first declared platform scope: Android API35+, GLES3, `arm64-v8a` production and `x86_64` emulator, with compileSdk36 because the inspected current QuickJS AAR requires it. API35 emulator remains valid with compileSdk36. This is an explicit initial scope, not a statement that API23–34 are impossible. Lowering minSdk is a separate Java-library/API audit.

The current probe already supplies useful CPU and rendering-loop evidence; `docs/android-status.md` honestly distinguishes it from image correctness, complete voxels or UI support. The stopped API35 TCG emulator and missing KVM affect verification speed/reliability, not the ability to implement or package these backends.

## GraalJS availability on ART

No supported Android ART drop-in distribution of the current GraalJS/Truffle host was found in the official documentation or artifact description. The [official 25.0.2 README](https://github.com/oracle/graaljs/blob/graal-25.0.2/README.md) documents compatible JVMs and Linux/macOS/Windows distributions, not ART. [Stock-JDK instructions](https://github.com/oracle/graaljs/blob/graal-25.0.2/docs/user/RunOnJDK.md) concern Oracle/OpenJDK JVMs; DEX conversion does not supply their APIs/runtime services. [Official Android issue3994](https://github.com/oracle/graal/issues/3994) reports a concrete Truffle/Unsafe failure on ART and is closed as not planned; it is historical corroboration, not a fresh execution test of version25.0.2.

Therefore current `ScriptUiRuntime` cannot responsibly be designated an Android backend. An Android Native Image target, a Linux ARM64 native binary, and running Java source through D8 are three different mechanisms; none establishes that `Context.newBuilder("js")` works in ART. A custom Graal native-image/JNI embedding would be a separate substantial port with its own toolchain, startup and artifact evidence. QuickJS Android already supplies the relevant maintained JNI mechanism. No categorical claim that all future/custom Graal-on-Android approaches are impossible is needed.

## Module boundaries and precise migration points

Keep `javity-core` and `javity-voxel` portable. `javity-core` only depends on libGDX core, and voxel only on core: neither needs Artemis, LWJGL or JS. Extract reusable application/demo scenes, resources and controls from `javity-desktop` into a `javity-samples` Java library if the full demos are needed; desktop launcher options/GLFW window management stay desktop-only.

Make `javity-ui` the platform-neutral Scene2D/declarative API. Introduce a narrow internal `YogaBackend`/`YogaNodeHandle` contract and two implementations: `javity-ui-yoga-lwjgl` (existing desktop implementation) and Android AAR `javity-ui-yoga-android`. `Flex`, `UtilityStyles`, `UiTheme`, and `UiDocument` currently directly import LWJGL Yoga; all five must migrate. Do not build a second Android fork of Flex/widgets. The handle API needs tree insert/remove/order, style copy, every already-supported style setter/getter, measurement, dirty state, calculation and layout reads, plus deterministic close. Backend instance selection occurs explicitly during launcher construction before creating any UI. Keep actor/theme/document ownership rules unchanged.

The Android adapter can use `new YogaNodeJNIFinalizer()`/`YogaConfigJNIFinalizer`, not fake Java layout. Map `YGNodeStyleSetGap` to `setGap(YogaGutter, float)`, numeric enums to their corresponding Java enums, `YGNodeCopyStyle` to `copyStyle`, mark-dirty to `dirty`, measurement to `YogaMeasureFunction` returning `YogaMeasureOutput.make(width,height)`, and geometry to `getLayoutX/Y/Width/Height`. Set root direction LTR before `calculateLayout`; set config defaults explicitly to match desktop. Match point rounding/config/errata; the same CSS class name does not guarantee identical versions/config defaults.

Handle lifecycle explicitly: before reparent/reorder remove children from their old Yoga parent; the Java binding enforces an owner. It has `removeChildAt` but no public equivalent of LWJGL's recursive free. Remove all children in reverse index order, clear measure/data references, free each owned node via public `YogaNodeJNIFinalizer.freeNatives()`, and free configs only after nodes. Merely dropping references or resetting nodes is not `close()`. Temporary intrinsic-measurement trees must also be freed, including exceptions. Keep measurement exceptions captured in Java and rethrown after layout, never through JNI. Preserve text dirtying, childrenOnly input, caller-owned detached children and Stage-vs-Yoga ownership contracts.

Split scripting into portable facade/host policy (`javity-script`), Graal implementation (`javity-script-graal`) and Android QuickJS adapter (`javity-script-quickjs-android`). The existing Java class exposes no Graal types publicly; its public bind/eval/tick/close contract can survive extraction. Replace internal `Value`/`Context`/`ProxyExecutable` assumptions with guest operations or an ID/JSON transport. Explicit factory injection is simpler than putting a desktop implementation on the Android dependency graph. Keep the existing convenience constructor on desktop only if it can resolve a provider without a hard Graal class reference in the portable facade.

Keep `javity-maplibre` outside the Android graph: it directly depends on LWJGL3, GLFW/EGL, FFM Native FFI and Linux runtime. It needs a separate MapLibre Android SDK integration, not shared native texture handles. Also note `javity-map-core/HttpTileFetcher` imports `java.net.http`, which is not Android's network API; adapt a transport interface to libGDX Net/Android HTTP before including online maps. Neither issue blocks the first requested core/voxel/UI/JS slice.

Create a real Android application module (new name such as `javity-android-app`; do not silently reuse legacy location/intent helpers). Add `google()` to plugin/dependency resolution as needed. Root build currently applies `java-library`, `options.release=25`, and JUnit configuration to every subproject; scope this convention to Java libraries instead of applying it to Android application/library projects. Keep ordinary JDK25 as desktop toolchain. AGP host-JDK/Gradle compatibility and D8 acceptance need independent explicit checks. The diagnostic R8 override is not proof that any chosen AGP works with Java25 bytecode.

For an API35-first port, retaining portable jar class major69 and selecting a verified D8 is possible (probe proves those classes on ART). A more conservative Android-specific shared-artifact variant can compile with JDK25 to an Android-supported release after source/API audit. Do not silently lower all desktop source levels or assume `--release17` backports `List.getFirst`, `Stream.toList`, records or all runtime APIs. Pin the actual production toolchain and run D8/R8 debug and release builds. A complete launcher must package assets/classpath resources, AndroidX, font/shader resources and natives; the probe's first missing-assets failure is directly relevant.

## Preserve authoring while changing JS transport

Keep the same generated host/sample/mm bundles and `web/javity-ui/src/runtime.js` imports: React, JavityReact, useAction/useSignal, View/Text/Button/Image/Progress/Toggle/Slider and existing prop validation remain. Do not ship a second React, browser DOM, WebView overlay or substitute CSS engine.

QuickJS-KT public `FunctionBinding`/`ObjectBinding` can exchange primitives and mapped collections, but the inspected API does not offer a Graal `Value` equivalent for retaining arbitrary guest functions. `JsFunction` is binding metadata, not an executable callback handle. The safe minimal adaptation is a JS-side registry: retain UI handlers, signal callbacks, timers, RAF and microtasks in JS; send only numeric/string IDs plus validated primitives/JSON across JNI. A bootstrap wrapper around `JavityNative.commit(json, handlerObject)` can retain the handler object and forward serializable metadata. Host events dispatch to the registry by ID in the correct context generation. Public TSX and gameplay action names remain unchanged.

The existing commit path calls `context.eval(JSON.parse(...))` inside a native callback. Replace this with Java/libGDX JSON parsing and schema validation; do not recursively invoke QuickJS evaluate from a binding callback. QuickJS-KT's evaluator is suspend-based and mutex/session controlled; do not `runBlocking` a dispatcher needed by itself or hand Scene2D work to `Dispatchers.Default`. Use a dedicated adapter that confines JS evaluations and UI mutations to the libGDX GL/UI thread, integrates suspension through a frame-drained queue, uses synchronous bindings for this first slice, and returns no pending Promise as a top-level render result. Alternatively implement an explicitly synchronous thin JNI wrapper around pinned QuickJS, but that adds native source/toolchain ownership which using the published AAR avoids.

Test and preserve signal/action reentrancy ordering: callbacks caused by actions while inside guest code must drain at a defined guest boundary without evaluating recursively through JNI; callbacks caused by Java outside guest execution can enter through the outer dispatcher. Keep event handlers transactional with commit success, controlled Toggle/Slider values, stale generation rejection and reload semantics. Syntax-check via compile before replacing a working runtime; runtime errors after replacement still close the new runtime rather than pretending Java side effects rolled back.

QuickJS-KT internally drains Promise jobs while evaluating; host callback count is not a universal runtime budget. Its inspected 1.0.15 API supports memoryLimit, maxStackSize, evaluationTimeoutMillis and interruptEvaluation. Decide those limits explicitly, ensure interruption is usable without waiting for a blocked GL loop, and verify cleanup. Treat bundled JS as application code, not process isolation. Close JS/unmount before UiDocument, then Yoga/theme/Stage in documented order on their owner thread.

## GLES shader work is more than a header edit

`SmoothShapeRenderer` hardcodes desktop `#version120` in vertex and fragment source. Fragment uses `fwidth`, so `antiAlias=false` still leaves a compile-time derivative reference. Introduce explicit desktop120 and GLES dialect generation, with material source injected into the same dialect. For GLES3 use `#version300 es`, explicit precision, vertex `in/out`, fragment `in`, explicit fragment output and `texture` instead of `texture2D`. Select it from actual GL capabilities/context, not merely OS. Preserve desktop shaders and all desktop pixel tests.

If GLES2 is also required, use GLSL ES100/no desktop version, precision and `GL_OES_standard_derivatives : enable` only when supported; compile an actual derivative-free fallback if unavailable. The shader also uses dynamic fragment uniform indexing (`u_points[i/2]`), integer control flow and 32 `vec4` point uniforms plus many other uniforms. These exceed some GLES2 minimum guarantees and cannot be fixed only by removing `#version120`. GLES3-first is a practical explicit initial scope; otherwise restructure constant indexing/chunking and query uniform limits. Validate shader error cleanup and material cache disposal on both dialects. Preserve shared-AA physical-framebuffer semantics.

`RectanglePainter` already has conditional GLES mediump precision and ES100-compatible syntax; it is a different shader and not the documented Shapes failure. Still test rounded images, UV atlas/flip, alpha/border, Polish FreeType text and GL-state restoration. If moving all shaders globally to ES300, do not globally prepend a header that breaks libGDX stock shader strings or this UI shader. Shader dialect should be per renderer.

## Smallest complete implementation sequence and acceptance

1. **Build graph + Android app:** root conventions scoped correctly, isolated Android launcher, real Android backend, production ARM64 and emulator x86_64 natives/assets. Pin compileSdk/AGP/Gradle/D8/JDK and min/target policy. Validate APK debug and minified release plus dependency/native contents. No Graal/LWJGL/FFM in Android runtime graph.
2. **Reusable scene + core/voxels/GLES:** run actual Game/component/model/voxel render path, GLES shaders, camera/FPS and deterministic touch controls (left movement, right look, jump/pause). Route UI first; ignore gameplay touches claimed by Stage. Pause/focus clears pointers/actions. Preserve negative-coordinate chunks, edit/rebuild generations and ownership. Include a small animated 3D asset and sprite fixture if claiming animations.
3. **Yoga adapter + native UI:** reusable Flex/widgets/classes through Android JNI, image/font assets, input/TextField keyboard and hitboxes. Run the same measured-layout/controlled-prop/reparent/dispose cases on both backends. Instrumented Android test creates and frees real Yoga nodes, then rendered screenshot/pixel evidence with no covering system dialogs.
4. **QuickJS adapter + same React bundles:** bind a Java gameplay action and primitive signal to TSX HUD. Demonstrate click/touch -> Java action -> updated signal -> React commit -> visible native widget in the same app as voxel scene. Test timers/pause, event/unmount cleanup, syntax/runtime reload failure, scene replacement, callbacks after close, error propagation and JS interruption. Verify packaged production bundles, not just a separate JS arithmetic sample.
5. **Lifecycle/device evidence:** resize/rotation/insets, Home/resume, Activity recreation and actual GL context/resource reload. Check unmanaged white textures/atlases/models and chunk GPU ownership, FreeType generator lifetime, shader/material caches and stale callback IDs. Do not equate pause/resume with context-loss proof.
6. **Broaden optional subsystems separately:** actual Box2D contacts/native disposal, audio API and playback, networking, MapLibre Android. Keep evidence and versioned scope per subsystem; do not defer the first core/UI/JS implementation until a phone is available.

On the present host, APK packaging, Java contracts, source implementation, DEX, JNI ABI inspection and backend unit tests are feasible. Software TCG can in principle establish a real API35 ART/JNI/GLES smoke if it stays responsive. It cannot establish ARM64 execution, phone GPU portability, thermal/memory behavior, physical touch/IME quirks, audio output or acceptable frame rate. Those are genuine external hardware/accelerated-CI evidence gaps. System UI ANRs under no-KVM TCG should be reported as environment failures with app logs and time bounds, not invented support passes or proof of an engine defect.
